The problem

Most platforms only inspect returns at the warehouse, days after pickup and often after the refund has gone out.

Real-world pattern · old-for-new swap

New headphones delivered. The old pair sent back.

A customer orders new headphones, keeps them, and returns the pair they already owned in the new box. Same brand, same shape at a glance, so a quick look at the warehouse can pass it. The seller refunds a new product and gets a used one back.

Fingerprint at the door

The shape and colour of the exact unit handed over are stored at delivery, so the return is compared with that unit, not with a catalogue photo.

Shape, not just colour

Dark navy and black are close for a colour check (2.6 ΔE, inside the normal range). Here the object-only DINOv2 shape match is what flagged the swap.

Label read blind

If the unit has a printed serial or model label, Gemini is told only where it was and must read it back. The match is checked in code.

Real photos and scores from ReturnGuard's test set (pair 49, python scripts/evaluate.py). Headphones are a hard case: the reverse swap (black delivered, navy returned) scored 0.82, close to genuine re-photos, so it went to a human reviewer instead.

How it works

Cheap evidence first. Expensive agents only when needed.

01

Fingerprint at delivery

3 photos at handover. Background removed, object-only DINOv2 embeddings and colour stored once. The identity agent reads labels, serials, marks and tags.

1 Gemini call per delivery
02

Free visual screen

Return photos are compared locally on shape and colour. Clearly different products are rejected and clear matches accepted with no LLM.

0 LLM calls · runs in parallel with policy + history
03

Agents when it's ambiguous

If a label exists, it's read blind and compared in code. If evidence still conflicts, a visual inspector compares all six photos.

0–2 Gemini calls per return
04

Explainable decision

Evidence becomes a 0–100 risk score with every contribution shown. Accept, human review or reject, plus a seller-ready evidence report.

Full audit trail in SQLite

What gets recorded
  • Background-removed cut-out of each view, checked for blur and framing.
  • Object-only DINOv2 embedding and median colour per view, computed once and stored.
  • Identity fingerprint from Gemini: printed identifiers (serial, batch, model), distinctive marks, accessories and tags.
  • An order ID assigned by the database at this moment.

What happens next
  1. Intake: background removal, capture-quality gate, features.
  2. In parallel: policy agent (return window), customer-history agent, visual screen.
  3. Triage router: fast reject / fast accept with no LLM, or call an agent.
  4. Identity agent: blind read of the label recorded at delivery.
  5. Visual inspector: all six photos, only if evidence still conflicts.
  6. Decision agent: evidence-weighted risk score and verdict.

System design

Architecture

Two entry points: delivery registration builds the fingerprint once; return verification is a LangGraph state machine where every LLM agent sits behind a cheaper check.

Design decisions

Why it's built this way

Object-only pooling, not plain patch-mean

Cut-outs are padded to a square. For tall items 65–77% of patches were padding, which made a shaker and a bottle score 0.77 "similar". Pooling only object patches drops that to 0.38.

A colour signal next to DINOv2

DINOv2 is trained to ignore colour. Median object chroma (ΔE in a*b*) separates the blue and black speakers that DINOv2 calls near-identical.

Blind label reading

The return-time identity agent is told where the label was, never what it said, and the comparison happens in code with fuzzy matching. It can't just agree with the expected answer.

Independent evidence

The visual inspector never sees the similarity scores or the label result, so its verdict is a second opinion, not an echo. Its prompt doesn't claim the items are the same product.

Structured outputs, transparent score

Every agent returns schema-validated JSON. The decision is an evidence-weighted log-odds score with each contribution shown, not a number the LLM made up.

Customer accounts feed the history agent

Signing in with email and phone creates a customer ID. Every delivery and return is tied to it, so the history agent can count earlier flagged returns and tighten the auto-accept cut-off for repeat offenders.

Every number explained in plain words

Reviewers see "colour difference 2.1, normal is under 2.8" rather than a bare score, plus which way each finding pushed the decision. Gemini's verdict, or the reason it wasn't needed, is always shown, and a second opinion can be requested on demand.

Fail safe, never stuck

Timeouts, retries with backoff and rate-limit handling. If an agent still fails, the return goes to a human instead of being auto-accepted, and nothing stays "processing" forever.

About ReturnGuard

The project

ReturnGuard verifies that a returned product is the unit that was delivered, using photos taken at the doorstep. It is decision support: clear cases are automated, ambiguous ones reach a person with the evidence already laid out.

Current evaluation data covers 6 physical items. Larger real-world datasets, a mobile capture app and integration with marketplace return flows are on the roadmap.
